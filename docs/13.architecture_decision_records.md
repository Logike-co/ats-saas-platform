# 📜 Registro de Decisiones Arquitectónicas (ADR)

Este documento consolida las decisiones arquitectonicas principales del ATS de LTI para fase MVP.

---

## ADR-001 - Monolito modular en backend

- **Estado:** Aceptada
- **Contexto:** Equipo de 1 desarrollador, bajo presupuesto y plazo de 2 meses.
- **Decision:** Implementar backend como monolito modular en NestJS.
- **Consecuencias:**
  - Menor complejidad operativa y despliegue.
  - Mayor velocidad de entrega en fase inicial.
  - Evolucion futura posible hacia servicios separados si la escala lo exige.

## ADR-002 - Frontend separado logicamente y API REST versionada

- **Estado:** Aceptada
- **Contexto:** Se busca mantener fronteras claras entre UI y negocio.
- **Decision:** Next.js consume backend via REST JSON versionado en `/api/v1`.
- **Consecuencias:**
  - Contratos claros y testeables.
  - Menor acoplamiento frontend-backend.
  - Facilidad para futuras integraciones externas.

## ADR-003 - Multi-tenant con `tenant_id` por fila

- **Estado:** Aceptada
- **Contexto:** Requisito SaaS multi-tenant con bajo costo de infraestructura.
- **Decision:** Shared DB/shared schema con aislamiento logico por `tenant_id`.
- **Consecuencias:**
  - Menor costo y simplicidad en MVP.
  - Obliga disciplina estricta en filtros por tenant.
  - Podra evaluarse `schema-per-tenant` en fase enterprise.

## ADR-004 - Autenticacion con Keycloak y frontend con NextAuth (OIDC)

- **Estado:** Aceptada
- **Contexto:** Necesidad de autenticacion robusta, MFA para admins y bajo esfuerzo de implementacion.
- **Decision:** Keycloak como IdP OIDC/OAuth2 y NextAuth como integracion de sesion en frontend.
- **Consecuencias:**
  - Seguridad estandarizada y escalable.
  - Menor complejidad frente a implementar auth propia.
  - Dependencia operativa de Keycloak en disponibilidad.

## ADR-005 - Persistencia PostgreSQL con Prisma ORM

- **Estado:** Aceptada
- **Contexto:** Productividad alta y mantenibilidad en TypeScript.
- **Decision:** Usar PostgreSQL como DB principal y Prisma para acceso a datos/migraciones.
- **Consecuencias:**
  - Mejor velocidad de desarrollo para MVP.
  - Migrations trazables y versionadas.
  - Necesidad de disciplina en cambios de esquema y despliegues.

## ADR-006 - Procesamiento asincrono con Redis + BullMQ

- **Estado:** Aceptada
- **Contexto:** Requerimiento de notificaciones por email y tareas diferidas sin bloquear UX.
- **Decision:** Implementar colas para notificaciones, recordatorios y trabajos no criticos.
- **Consecuencias:**
  - Mejora de latencia percibida en operaciones interactivas.
  - Mayor resiliencia con reintentos.
  - Agrega complejidad operativa moderada (worker + monitoreo de cola).

## ADR-007 - Infraestructura single-VPS con Docker Compose, Nginx y TLS

- **Estado:** Aceptada
- **Contexto:** Restriccion de costo bajo en fase inicial.
- **Decision:** Despliegue en un VPS unico con Docker Compose, Nginx como reverse proxy y certificados Let's Encrypt.
- **Consecuencias:**
  - Costo minimo y operacion simple.
  - Punto unico de falla aceptado en MVP.
  - Base clara para evolucion posterior a topologias mas resilientes.

## ADR-008 - Gobernanza de calidad obligatoria

- **Estado:** Aceptada
- **Contexto:** Se requiere alta mantenibilidad con equipo reducido.
- **Decision:** TDD obligatorio, cobertura 90% en logica critica, CI obligatorio con lint/format/tests.
- **Consecuencias:**
  - Menor probabilidad de regresiones.
  - Mayor esfuerzo inicial por cambio.
  - Mejor velocidad sostenida a mediano plazo.
