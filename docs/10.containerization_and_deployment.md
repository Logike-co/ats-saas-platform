# 📦 Contenerización y Despliegue

## Objetivo de la Estrategia

Disponer de un proceso de build y despliegue **liviano, rapido y repetible**, priorizando:

- bajo consumo de recursos en VPS;
- arranque rapido de servicios;
- simplicidad operativa para 1 desarrollador.

## Contenerizacion por Servicio

### Imagen base

- `node:20-alpine` para `frontend` y `backend`.

### Construccion

- **Multi-stage build obligatorio** para reducir tamano final de imagen.
- Dependencias de compilacion solo en etapa builder.
- Imagen runtime minima con artefactos finales y sin toolchain innecesario.

### Buenas practicas

- ejecutar como usuario no root;
- definir `HEALTHCHECK`;
- fijar `NODE_ENV=production` en runtime;
- minimizar capas y limpiar cache del package manager.

## Docker Compose por Entorno (Recomendacion)

Se recomienda usar:

- `docker-compose.yml` (base comun)
- `docker-compose.dev.yml` (overrides de desarrollo)
- `docker-compose.prod.yml` (overrides de produccion)

Razon:

- evita duplicacion;
- simplifica mantenimiento;
- permite cambiar solo lo necesario por entorno (volumenes, debug flags, replicas, etc.).

## Gestion de Variables de Entorno

Se recomienda:

- `.env` para valores base locales;
- `.env.dev` para desarrollo;
- `.env.prod` para produccion;
- nunca versionar secretos reales en Git.

En CI/CD, secretos sensibles deben venir desde GitHub Secrets.

## Registro y Versionado de Imagenes

- Registry: **GHCR (GitHub Container Registry)**.
- Tags:
  - `latest` para referencia rapida,
  - `vX.Y.Z` para versionado inmutable de release.

## Pipeline de Build y Publicacion

En push a `main`:

1. Ejecutar lint, format check y tests.
2. Construir imagenes frontend/backend.
3. Publicar imagenes en GHCR (`latest` y tag semantico).
4. Generar artefactos/metadatos de release.

## Estrategia de Despliegue Inicial

Se mantiene **despliegue manual gatillado** (no auto-deploy) para reducir riesgo en etapa temprana:

1. Backup DB previo.
2. `docker compose pull`
3. `docker compose up -d`
4. Verificacion de health checks.
5. Smoke test funcional rapido.

### Rollback

- revertir a tag previo estable y levantar nuevamente compose;
- restaurar backup de DB solo si hubo migracion incompatible.

## Migraciones Prisma en Produccion (Como Funciona)

### Flujo recomendado

1. En desarrollo se generan migraciones con `prisma migrate dev`.
2. Los archivos SQL/versiones quedan en el repositorio.
3. En produccion **no se recalcula el esquema**; se aplican solo migraciones existentes con:
   - `prisma migrate deploy`

### Que hace `prisma migrate deploy`

- revisa tabla interna de historial de Prisma;
- detecta migraciones pendientes;
- aplica en orden las faltantes;
- no crea migraciones nuevas en produccion.

### Donde ejecutarlo

Opcion recomendada en tu caso:

- Ejecutar `prisma migrate deploy` al inicio del contenedor de backend (entrypoint) antes de arrancar la API.

Ventajas:

- asegura compatibilidad esquema-codigo en cada despliegue;
- evita pasos manuales olvidados.

Precaucion:

- si una migracion falla, backend no debe arrancar y se activa protocolo de rollback.

## Consideraciones de Rendimiento y Arranque

- usar build cache en CI para acelerar imagenes;
- reducir dependencias runtime;
- habilitar compresion en Nginx;
- preconstruir frontend (`next build`) y servir en modo produccion;
- separar workers de colas si la carga crece.
