| Categoria | Tecnologia | Proposito |

## Unica responsabilidad (SRP) e interfaz segregada (ISP) en todo el backend

El **principio de unica responsabilidad** aplica a **cualquier** funcionalidad del backend del ATS, no solo a pantallas de administracion: cada clase o modulo cohesivo debe tener **una razon principal de cambio** (una intencion de aplicacion o de infraestructura acotada).

Practicas obligatorias en NestJS (alineadas con `specs/.agents/rules/architecture-standards.mdc`):

- **Controllers:** validacion de entrada y delegacion; **sin** logica de dominio ni acceso directo a Prisma, repositorios concretos o queries ad hoc.
- **Casos de uso (puertos de entrada):** uno por intencion de aplicacion clara (comando o consulta); la implementacion tipica es **una clase Service por UseCase**, salvo excepcion documentada (ADR).
- **Puertos de salida (ISP):** interfaces **pequenas y segregadas**; evitar un unico puerto “repositorio gigante” salvo que el equipo lo justifique por ADR. Si mezclar metodos en una sola interfaz obligaria a implementaciones vacias o poco cohesionadas, separar puertos.
- **Dominio:** entidades y reglas preferentemente **sin** Nest, Prisma ni HTTP.

La seccion siguiente define un **perfil obligatorio adicional** cuando la US describe **administracion, ABM, CRUD o gestion** de una entidad persistida: los **cinco** puertos de entrada estandar y la estructura de carpetas detallada.

## Pantallas de administracion: hexagonal estricta y CRUD completo (NestJS)

Cuando una **historia de usuario** o ticket indique **pantalla de administracion**, **ABM**, **CRUD** o **gestion** de una entidad de dominio persistida, ademas del **SRP e ISP transversales** descritos arriba, el backend debe planificarse e implementarse con **arquitectura hexagonal / clean** en la forma que sigue. No se acepta un unico servicio monolitico que mezcle todas las operaciones de esa entidad sin puertos ni casos de uso acotados.

### Dependencias (solo hacia adentro)

| Capa | Responsabilidad |
| :--- | :--- |
| **`domain`** | Entidades, value objects, reglas puras. **Sin** Nest, Prisma, HTTP ni filesystem. |
| **`application`** | **Puertos de entrada** (casos de uso) y **puertos de salida** (interfaces hacia persistencia). Orquestacion en **implementaciones** de un solo caso de uso por clase. |
| **`infrastructure`** | Adaptadores: Prisma, archivos, colas, clientes HTTP. Implementan **puertos de salida**. |
| **`api`** | Controllers: validacion DTO, mapeo minimo, **solo invocan puertos de entrada** (casos de uso). **Prohibido** inyectar repositorios Prisma o ejecutar queries desde el controller. |

### Casos de uso obligatorios (entidad administrada)

Para cada entidad gestionada en administracion se definen **cinco** puertos de entrada (interfaces), cada uno con **una** implementacion inyectable:

| Puerto de entrada (inbound) | Metodo | Proposito |
| :--- | :--- | :--- |
| `Create{Entity}UseCase` | `execute(command)` | Alta (mutacion). |
| `Update{Entity}UseCase` | `execute(command)` | Actualizacion (mutacion). |
| `Delete{Entity}UseCase` | `execute(command)` | Baja logica o fisica segun dominio (mutacion). |
| `Find{Entity}ByIdUseCase` | `query(query)` | Detalle por id (solo lectura). |
| `Search{Entities}UseCase` | `query(criteria)` | Listado **paginado** con **criterios de filtro** explícitos (solo lectura). |

Convencion de metodos:

- **`execute`**: comandos que **mutan** estado.
- **`query`**: operaciones de **solo lectura** (FindById, Search).

`{Entity}` / `{Entities}` en **PascalCase** en nombres de tipo (ingles), acorde al dominio (ej. `Candidate`, `Candidates`).

### Puertos de salida (ISP estricto)

Cada dependencia hacia persistencia se expone como **interfaz unica por responsabilidad** (Interface Segregation). Ejemplos orientativos para la entidad `{Entity}`:

| Puerto de salida (outbound) | Rol |
| :--- | :--- |
| `Create{Entity}Port` o `Insert{Entity}Port` | Persistir registro nuevo. |
| `Update{Entity}Port` | Aplicar cambios a un registro existente. |
| `Delete{Entity}Port` | Eliminar o marcar borrado. |
| `Find{Entity}ByIdPort` | Obtener uno por id **y tenant**. |
| `Search{Entities}Port` | Consulta con filtros, orden y paginacion. |

Evitar un unico `RepositoryPort` gigante salvo que el equipo documente una excepcion mediante ADR. Preferir **varas interfaces pequenas** alineadas a cada caso de uso o a grupos minimos cohesivos.

Las implementaciones en `infrastructure` usan sufijo **`Adapter`** (ej. `CandidatePersistenceAdapter` implementando varios puertos de salida **solo si** cada metodo sigue siendo cohesivo; si no, **un adapter por puerto**).

### Implementaciones de aplicacion

- Cada **`Create{Entity}Service`** implementa **`Create{Entity}UseCase`** y recibe por constructor **solo** los `Port` de salida que necesite (típicamente `Create{Entity}Port` y, si aplica, lecturas para validar unicidad).
- Misma regla para `Update`, `Delete`, `FindById`, `Search`: **una clase por caso de uso**, dependencias minimas.

### API REST alineada (bajo `/api/v1`)

| Operacion HTTP | Caso de uso |
| :--- | :--- |
| `POST /...` | `Create{Entity}UseCase.execute` |
| `PATCH` o `PUT /.../:id` | `Update{Entity}UseCase.execute` |
| `DELETE /.../:id` | `Delete{Entity}UseCase.execute` |
| `GET /.../:id` | `Find{Entity}ByIdUseCase.query` |
| `GET /...` (lista) | `Search{Entities}UseCase.query` con **query params** documentados (filtros, `page`, `pageSize`, `sort`, etc.). |

`tenant_id` siempre desde **contexto de seguridad**, nunca como unico criterio de confianza enviado por el cliente sin validacion.

### Search: criterios y filtros

El plan y el codigo deben dejar explícito:

- **Parametros de filtro** permitidos (texto, estado, fechas, ids relacionados).
- **Paginacion**: al menos `page` y `pageSize` (o `cursor` si se acuerda).
- **Ordenacion** opcional (`sortBy`, `sortOrder`).
- Respuesta: lista + **total** o **nextCursor** para la UI de administracion.

### Estructura de carpetas recomendada (por feature)

Raiz del feature bajo `ATS/apps/backend/src/` (ajustar si el repo usa `src/modules/{feature}`):

```text
{feature}/
  {feature}.module.ts
  api/
    {feature}.controller.ts
    dto/
      create-{entity}.dto.ts
      update-{entity}.dto.ts
      search-{entities}.query.dto.ts   # query params + validacion
  application/
    ports/
      in/
        create-{entity}.use-case.ts
        update-{entity}.use-case.ts
        delete-{entity}.use-case.ts
        find-{entity}-by-id.use-case.ts
        search-{entities}.use-case.ts
      out/
        create-{entity}.port.ts
        update-{entity}.port.ts
        delete-{entity}.port.ts
        find-{entity}-by-id.port.ts
        search-{entities}.port.ts
    services/
      create-{entity}.service.ts
      update-{entity}.service.ts
      delete-{entity}.service.ts
      find-{entity}-by-id.service.ts
      search-{entities}.service.ts
  domain/
    {entity}.entity.ts               # o modelos de dominio equivalentes
  infrastructure/
    persistence/
      {entity}.prisma-adapter.ts       # implementa ports out
```

Nombres de archivo en **kebab-case**; tipos/clases en **PascalCase**.

### Registro en NestJS

- Cada **Service** se declara como `provider` y se asocia al token del **UseCase** (`useClass` o `useFactory`) para que el **Controller** dependa de la **abstraccion** (`@Inject(CREATE_ENTITY_USE_CASE)` o interfaz con token simbolico).

### Referencia cruzada

- Planificacion detallada de archivos por ticket: **`specs/.commands/plan-backend-ticket.md`** (SRP en **todo** ticket; checklist de cinco casos de uso cuando la US sea administracion / CRUD de entidad).
- Reglas operativas para el agente: **`specs/.agents/rules/architecture-standards.mdc`**.

## API y Contratos

- Estilo: **RESTful JSON**.
- Versionado: `/api/v1`.
- Validacion de entrada backend: `class-validator` + `class-transformer`.
- Validacion frontend: `zod` para formularios y contratos de consumo.
- Convencion de respuesta de error: `code`, `message`, `traceId`, `details`.

### Ejemplo de contrato: directorio de candidatos

Referencia alineada con `docs/02.functional_summary.md` y `docs/08.data.md`:

| Operacion | Metodo y ruta | Notas |
| :--- | :--- | :--- |
| Crear candidato | `POST /api/v1/candidates` | Cuerpo JSON con campos del DTO; `tenant_id` desde contexto JWT, **no** desde el cliente. |
| Subir CV | `POST /api/v1/candidates/:id/cv` | `multipart/form-data`; PDF/DOCX; validar MIME y tamano max. (p. ej. 5–10 MB). |
| Conflicto email duplicado | `409` o `422` | Codigo estable `CANDIDATE_EMAIL_DUPLICATE` (o equivalente documentado). |
| Creado | `201 Created` | Cuerpo con `id` y datos minimos; opcional cabecera `Location`. |

**Errores de validacion:** `400` con `details` por campo cuando sea posible, para enlazar mensajes en el formulario.

**Autorizacion:** roles **Recruiter** y, si se define en producto, **Admin RRHH**; negar el resto salvo excepcion documentada.

## Autenticacion y Sesion (Recomendacion)

Se recomienda **NextAuth con proveedor OIDC (Keycloak)** para frontend.

Razon:

- integracion nativa con Next.js y middleware;
- manejo de sesion seguro en servidor;
- menor complejidad que implementar flujo OIDC manual;
- facilita proteccion de rutas por rol.

### Flujo resumido

1. Usuario inicia sesion en Keycloak.
2. NextAuth gestiona callback OIDC y sesion.
3. Frontend consume API con access token.
4. Backend valida JWT (issuer, audience, firma, expiracion) y rol.
5. Capa tenancy fuerza `tenant_id` en contexto por solicitud.

## Diseno Asincrono y Colas

Las colas se aplican en `notifications` y tareas diferidas:

- envio de emails transaccionales;
- recordatorios de entrevistas;
- reintentos ante fallos de SMTP;
- procesos no bloqueantes de auditoria/eventos.

### Patron de uso

- El caso de uso principal persiste cambios.
- Se emite evento interno.
- Se encola job BullMQ.
- Worker procesa, registra resultado y aplica reintentos.

## Convenciones de Codigo

- Idioma de codigo: ingles.
- Idioma funcional/documentacion: espanol.
- Tipado estricto obligatorio en TypeScript (`strict: true`).
- Naming consistente por feature y responsabilidad.

## Testing y TDD

- **TDD obligatorio** para desarrollo nuevo.
- Unit tests en frontend (Vitest) y backend (Jest).
- E2E con Playwright para flujos criticos.
- Cobertura minima objetivo: `90%` en logica critica.

## Logging, Metricas y Salud

- Logging estructurado con `pino`.
- Correlacion por `traceId`.
- Exposicion de health checks para API, DB, Redis y dependencias criticas.
- Metricas operativas para latencia, errores y throughput.

## Pipeline CI (GitHub Actions)

Pipeline minimo obligatorio en cada pull request:

1. Instalacion de dependencias (`pnpm`).
2. Lint.
3. Format check.
4. Tests unitarios.
5. Tests E2E (segun estrategia por rama/entorno).

No se permite merge si alguna validacion falla.
